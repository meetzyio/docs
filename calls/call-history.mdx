# Call History

The Call History section provides a comprehensive view of all calls made by your AI agents. You can search, filter, and analyze call data to monitor performance and identify insights with powerful filtering capabilities and customizable views.

## Accessing Call History

Navigate to **Calls** in the main menu to access your complete call history.

<Info>
There is now an improved calls view (**Calls v2**) with **fully configurable, drag-and-drop columns**, **dynamic input/output field discovery grouped by agent**, **saved views**, **real AI latency metrics with a per-turn detail chart**, a **searchable agent combobox**, an **exact-match Call ID filter**, and an **Excel export that mirrors your visible columns**. It's available alongside the classic Call History table and shares the same underlying data — use it whenever you need deeper performance visibility or a more tailored column layout.
</Info>

## Interface Overview

The calls interface consists of:

| Section | Description |
|---------|-------------|
| 📊 Header | Title, description, and selection status |
| 🔍 Filter Bar | Advanced filtering controls with visibility management |
| ⚙️ Columns | Configurable, draggable columns including dynamic agent fields, plus saved views |
| 📋 Call Table | List of all calls with key information |
| 📄 Details Modal | Detailed view of individual calls, including a full AI latency chart |

## Configurable Columns

<Info>
The improved calls view lets you fully control which columns appear, in what order, and even add columns sourced directly from each agent's input parameters or structured output — no need to open a call individually to see a specific data point.
</Info>

Click the **⚙️ Columns** button above the table to open the column manager panel. It's organized into four sections:

| Section | Purpose |
|---------|---------|
| **Saved views** | Save your current column configuration under a name and reapply it later with one click |
| **Input columns** | Discover fields from each agent's input parameters (`call.data`) and add them as columns, grouped by agent |
| **Columns** | Manage visibility and order of all currently active columns — fixed and dynamic — via drag and drop |
| **Output columns** | Discover fields from each agent's structured output (`call.output`) and add them as columns, grouped by agent |

<Steps>
<Step title="Open the Column Manager">
Click the **⚙️ Columns** button next to the Export to Excel button to open the column configuration drawer.
</Step>
<Step title="Reorder Columns">
In the **Columns** section, drag any row using the ⠿ handle to reorder it. The table updates its column order live as you drag.
</Step>
<Step title="Show or Hide Columns">
Use the checkbox next to each column name to toggle its visibility. Columns marked as non-toggleable (such as **Actions**) always remain visible.
</Step>
<Step title="Add a Dynamic Column from Input or Output">
Expand **Input columns** or **Output columns**, find the field you need under the relevant agent group, and click **Add**. The field appears immediately as a new column, placed just before the Actions column, and is tagged with an **input**/**output** badge in the Columns list.
</Step>
<Step title="Remove a Dynamic Column">
Dynamic columns display a small ✕ button next to their badge in the Columns list. Click ✕ to remove them from your view entirely.
</Step>
<Step title="Reset to Defaults">
Click **Reset to default columns** at the bottom of the panel to discard all customizations and restore the original column set.
</Step>
</Steps>

<Tip>
Your column configuration — order, visibility, and any dynamic columns you've added — is saved automatically per user and restored the next time you open the view. There's no manual save step.
</Tip>

<Warning>
Dynamic columns are tied to the agent and field path they were created from. If an agent stops sending a particular input or output field, that column will simply show empty values for calls where the data is missing, rather than being removed automatically.
</Warning>

### Saved Views

<Info>
Beyond your single auto-saved layout, the column manager lets you keep multiple **named views** — for example, one focused on latency troubleshooting and another focused on evaluation outcomes — and switch between them instantly.
</Info>

The **Saved views** section sits at the top of the column manager panel:

<Steps>
<Step title="Configure a Layout">
Show, hide, reorder, and add dynamic columns until the table matches the view you want to save.
</Step>
<Step title="Name and Save">
Type a name into the **New view name…** field and click **Save**. The current column configuration is stored as a new saved view.
</Step>
<Step title="Apply a Saved View">
Click on any saved view's name in the list to instantly replace your current column configuration with that view's layout.
</Step>
<Step title="Delete a Saved View">
Click the ✕ next to a saved view to remove it. This only deletes the saved view itself — it doesn't change your currently active columns.
</Step>
</Steps>

<Tip>
Saved views only capture the **column configuration** (which columns, their order, and visibility) — they don't store filters, sorting, or page size. Combine a saved view with a filter preset for a fully repeatable workflow.
</Tip>

### Legacy Column Configuration Migration

<Info>
If you previously customized columns in the classic Call History table, that layout isn't lost — the improved view automatically imports it the first time you open it.
</Info>

The first time a user opens the improved calls view without any existing saved preferences, the system performs a **one-time, automatic migration**:

| Step | What happens |
|------|--------------|
| 1 | The improved view checks your browser's local storage for a legacy column configuration saved from the classic Call History table |
| 2 | Fixed columns that exist in both the old and new default sets carry over their visibility setting |
| 3 | Any dynamic input or output columns you had added in the classic table are reconstructed as-is, keeping their label, path, and source |
| 4 | Your previous sort column, sort direction, and page size are applied if present |
| 5 | The migrated configuration is saved to your account immediately, so it's available even if you switch devices or browsers afterward |

<Warning>
This migration is read-only and runs only once. It reads from the browser's local storage, so it only applies on the same browser/device where you originally customized the classic table. If you've already opened the improved view before, or already have saved preferences for it, the migration is skipped and your existing improved-view configuration is used instead.
</Warning>

## AI Latency Metrics

<Info>
Every call now tracks how quickly your AI agent responded throughout the conversation, giving you a direct signal of conversational responsiveness independent of call outcome or duration.
</Info>

The improved view surfaces AI latency at three levels of detail:

| Metric | Column | Description |
|--------|--------|-------------|
| **Average latency** | Avg AI latency | The mean AI response latency (in milliseconds) across all turns in the call |
| **Maximum latency** | Max latency | The single highest response latency recorded during the call — useful for spotting worst-case delays |
| **Per-turn sparkline** | Latency (turns) | A compact inline chart showing how latency evolved turn by turn, without leaving the table |

<Steps>
<Step title="Scan Averages at a Glance">
Sort the table by **Avg AI latency** to quickly identify calls or agents with consistently slow responses.
</Step>
<Step title="Spot Outliers with Max Latency">
Enable the **Max latency** column (hidden by default) to catch calls with an isolated but severe delay that the average might hide.
</Step>
<Step title="Read the Sparkline">
The **Latency (turns)** column renders a lightweight line for each call, plotting latency per turn. A rising line toward the end of a call can indicate the agent slowing down as the conversation got more complex.
</Step>
<Step title="Open the Full Latency Detail Modal">
Click into a call's details to open the dedicated AI latency modal: a full, interactive chart plotting latency per turn, with exact millisecond values on hover and the timestamp of each turn along the X axis.
</Step>
</Steps>

### Latency Detail Modal

<Info>
The latency detail modal turns the compact table sparkline into a full-size, turn-by-turn chart so you can pinpoint exactly where a call slowed down.
</Info>

| Feature | Description |
|---------|-------------|
| **Per-turn chart** | Every AI turn in the call is plotted as a point, connected in chronological order |
| **Exact values on hover** | Hovering a point shows the precise latency in milliseconds for that specific turn |
| **Timestamp axis** | The X axis reflects when each turn occurred during the call, making it easy to correlate spikes with a stage of the conversation |
| **Visual outlier detection** | Sudden jumps in the line stand out immediately compared to scanning raw numbers in a table |

<Tip>
Combine latency metrics with the LLM and LLM detail columns to check whether latency spikes correlate with a model cascade fallback — a secondary model taking over mid-call can sometimes explain a sudden increase in response time. Open the latency detail modal and the LLM detail breakdown side by side for the same call to confirm.
</Tip>

<Warning>
Latency data depends on the underlying voice provider reporting response timing for each turn. Calls made before latency tracking was enabled, or through integrations that don't report this data, will show empty values for these columns and an empty chart in the detail modal.
</Warning>

## Recording Player with Waveform

<Info>
The recording player has been upgraded from a simple audio control to a full waveform-based player, built from the actual decoded audio of the call — not a generic placeholder animation.
</Info>

Click the **Recording** column on any call to open the player modal, which includes:

| Feature | Description |
|---------|-------------|
| **Real waveform** | Rendered directly from the decoded audio, showing actual amplitude across the call |
| **Click-to-seek** | Click anywhere on the waveform to jump to that point in the recording |
| **Playback progress** | The waveform visually fills in as the recording plays, distinguishing played from unplayed audio |
| **Skip controls** | Jump backward or forward 10 seconds with dedicated buttons |
| **Playback speed** | Choose from 0.5x, 0.75x, 1x, 1.25x, 1.5x, or 2x speed |
| **Synced transcript** | The call transcript loads alongside the player for side-by-side review |
| **Download** | Download the recording file directly from the modal |

<Steps>
<Step title="Open the Player">
Click the Recording column for any call with an available recording.
</Step>
<Step title="Review the Waveform">
Wait for the audio to load and decode — the waveform renders automatically once ready, reflecting the real amplitude of the call.
</Step>
<Step title="Seek and Adjust Speed">
Click on any part of the waveform to jump there instantly, or use the speed buttons to review a section more quickly or more carefully.
</Step>
<Step title="Cross-Reference with the Transcript">
Use the transcript panel next to the player to follow along with what's being said as you scrub through the recording.
</Step>
</Steps>

<Tip>
Because the waveform is built from decoded audio rather than a static image, longer recordings may take a moment to render on first open. Once decoded, seeking and speed changes are instant.
</Tip>

## Advanced Filter System

### Filter Visibility Configuration

<Info>
Customize which filters are visible in your interface to streamline your workflow and focus on the most relevant filtering options.
</Info>

A dedicated **⚙️ settings button** is located at the end of the Filter Bar, next to the filter controls. It opens a configuration panel that lets you show or hide individual filters without affecting your applied filter values.

<Steps>
<Step title="Open Filter Settings">
Click the ⚙️ settings icon at the right end of the Filter Bar to open the filter visibility panel.
</Step>
<Step title="Toggle Individual Filters">
Use the checkboxes to show or hide each of the following filters independently:

- **Goal** — filter calls by the agent's configured goal or objective
- **Tags** — filter by dynamic or custom tags
- **Evaluations** — filter by evaluation completion or outcome
- **Call ID** — the direct database lookup search field, matched on the exact ID

Core filters such as Date Range, Agents, Status, Direction, and Success are always visible and cannot be hidden, since they are considered essential for everyday use.
</Step>
<Step title="Apply and Close">
Close the panel by clicking outside of it or pressing the settings icon again. Hidden filters are immediately removed from the Filter Bar, freeing up space for the ones you actually use.
</Step>
<Step title="Automatic Persistence">
Your filter visibility preferences are saved automatically per user and restored the next time you open Call History — no need to reconfigure them on every visit.
</Step>
</Steps>

<Info>
By default, the **Tags** filter is now visible in the Filter Bar out of the box, so you don't need to open the settings panel to start filtering calls by tags. Goal, Evaluations, and Call ID remain part of the same visibility configuration and follow their own default state, which you can adjust at any time.
</Info>

<Tip>
If a filter is hidden but has an active value from a previous session, it will remain applied to your results even though it's not visible. Re-enable the filter from the settings panel to review or clear it. Look for the 👁️ **Hidden Filter** indicator near the settings icon — it appears whenever a hidden filter still holds an active value, so you always know your results are being narrowed by something you can't currently see.
</Tip>

### Exact Call ID Search

<Warning>
When using Call ID search, all other filters are temporarily disabled to ensure precise lookups.
</Warning>

The Call ID filter performs a **direct, exact-match** database lookup and has **exclusive priority over every other filter** in the Filter Bar. As soon as you start typing a value into the Call ID field, all remaining filters (Date Range, Agents, Status, Direction, Success, Goal, Tags, and Evaluations) become visually disabled and are excluded from the query — the interface greys them out and blocks interaction with them to make it clear that only the Call ID lookup is active.

<Info>
Think of it as a small measurement problem: the moment you observe the system through a Call ID, every other possible filter state "collapses" — much like a quantum measurement collapsing a wave function into a single outcome. Before you type an ID, the Filter Bar exists in a superposition of Date Range, Agents, Status, Direction, Success, Goal, Tags, and Evaluations, all potentially active at once. The instant a Call ID value is present, that superposition resolves into a single, deterministic state: exactly one call, found by its exact ID, with no other filter contributing to the result.
</Info>

Enhanced Call ID functionality with database search:

<Steps>
<Step title="Enter Call ID">
Type the specific call ID in the dedicated search field. As soon as a value is present, the rest of the filters switch to a disabled visual state.
</Step>
<Step title="Database Query">
The system performs a direct database lookup for the exact call ID, ignoring any values currently set in other filters. Partial or fuzzy matches are not returned — the ID must match exactly.
</Step>
<Step title="Instant Results">
The matching call is displayed immediately, bypassing all other filters.
</Step>
<Step title="Clear Search">
Remove the call ID to restore normal filtering functionality. All previously configured filters are automatically re-enabled and reapplied — the "superposition" is restored exactly as you left it.
</Step>
</Steps>

<Tip>
Like the Goal and Evaluations filters, the Call ID field is hidden from the Filter Bar by default and can be enabled from the filter visibility settings (⚙️) whenever your workflow requires manual, exact ID lookups.
</Tip>

<Warning>
This priority behavior is exclusive and non-negotiable: while a Call ID value is present, there is no way to combine it with Date Range, Agents, Status, Direction, Success, Goal, Tags, or Evaluations. If you need a combined search, clear the Call ID field first and use the other filters instead.
</Warning>

### LLM and LLM Detail Columns

<Info>
These two columns surface the underlying language model activity for every call, which is especially useful for agents built on ElevenLabs' conversational stack, where a **model cascade** can automatically fall back to a secondary model mid-call if the primary one becomes unavailable or degrades.
</Info>

| Column | What it shows |
|--------|---------------|
| **LLM** | The distinct model(s) used during the call, listed in the order they were engaged (e.g. a single model like `gpt-4o`, or multiple models such as `gpt-4o + gpt-4o-mini` if a fallback occurred). |
| **LLM detail** | An expandable, turn-by-turn breakdown showing exactly which model handled each conversational turn and at what point in the call the switch happened. |

<Steps>
<Step title="Enable the Columns">
Open the column manager above the Call Table and toggle on **LLM** and/or **LLM detail** to add them to your view.
</Step>
<Step title="Read the LLM Column">
Each row shows the model(s) used for that call. A single model name means the call ran entirely on the primary model with no fallback.
</Step>
<Step title="Spot Degradations">
When a call shows **more than one model** in the LLM column, it means the ElevenLabs cascade degraded at least once during the call — falling back from the primary model to a secondary one. This is the same detection logic used in the call details modal.
</Step>
<Step title="Drill Into LLM Detail">
Expand the LLM detail column (or open the call in the Details Modal) to see the exact timestamp of each turn and which model produced it, helping you pinpoint when and why a degradation happened.
</Step>
</Steps>

<Tip>
Use the LLM column together with the Status and Success filters to quickly check whether cascade degradations correlate with lower success rates or specific agents, then dig deeper with LLM detail on the affected calls.
</Tip>

<Warning>
For calls made before model cascade tracking was introduced, the LLM column falls back to the legacy single `model_used` value when no multi-model data is available. In that case, no degradation can be detected for those older calls.
</Warning>

## Performance and Optimization

### Smart Loading

The system includes several performance optimizations:

- **Lazy Loading** - Calls load as you scroll through the table
- **Filter Debouncing** - Prevents excessive API calls while typing
- **Caching** - Frequently accessed data is cached for faster loading
- **Background Refresh** - New calls appear automatically without manual refresh

### Search Optimization

<Tip>
Use specific search criteria to improve performance when working with large datasets.
</Tip>

Best practices for efficient searching:

1. **Start with Date Range** - Narrow down the time period first
2. **Use Specific Agents** - Filter by particular agents using the searchable combobox when possible
3. **Combine Filters Strategically** - Use multiple filters to reduce result sets
4. **Save Common Searches** - Use presets for frequently used filter combinations
5. **Reach for Call ID Last** - Only use the exact-match Call ID search when you need one specific call; remember it overrides every other filter combination you've built up

### Targeted Debugging with Call ID

<Steps>
<Step title="Enable the Call ID Filter">
Open the ⚙️ filter settings panel and enable the Call ID filter if it isn't already visible in your Filter Bar.
</Step>
<Step title="Locate the Call ID">
Copy the call ID from a support ticket, log entry, or the Quick Actions "Copy ID" option.
</Step>
<Step title="Paste into Call ID Search">
Enter the ID into the Call ID field. All other filters are immediately disabled to avoid conflicting results — the Filter Bar's superposition of possible states collapses into this single, deterministic, exact-match lookup.
</Step>
<Step title="Review the Exact Match">
The system performs a direct database lookup and returns the single matching call, regardless of any date range or agent filter previously applied.
</Step>
<Step title="Clear to Resume">
Clear the Call ID field once you're done to automatically restore your previous filter configuration.
</Step>
</Steps>

### Investigating LLM Cascade Degradations

<Steps>
<Step title="Enable the LLM Columns">
Open the column manager and turn on **LLM** and **LLM detail** for your Call Table view.
</Step>
<Step title="Scan for Multiple Models">
Look for rows where the LLM column lists more than one model — this flags a cascade degradation during that call.
</Step>
<Step title="Open LLM Detail">
Expand LLM detail (or open the Details Modal) to see the exact turn where the switch happened and which model took over.
</Step>
<Step title="Cross-Reference Outcomes">
Combine this with the Success and Status filters to check whether degraded calls correlate with lower success rates.
</Step>
</Steps>

### Diagnosing a Slow Agent with Latency Metrics

<Steps>
<Step title="Sort by Avg AI Latency">
In the improved calls view, click the **Avg AI latency** column header to sort calls from slowest to fastest.
</Step>
<Step title="Enable Max Latency">
Open the column manager and enable **Max latency** to see whether the slowdown is consistent or driven by a few extreme turns.
</Step>
<Step title="Check the Sparkline Pattern">
Look at the **Latency (turns)** sparkline for affected calls — a steadily rising line suggests the agent degraded as the call progressed.
</Step>
<Step title="Open the Latency Detail Modal">
Click into the call to open the full latency detail modal and identify exactly which turn, and at what timestamp, caused the spike.
</Step>
<Step title="Correlate with LLM Detail">
Check the LLM detail column for the same call to see if a model cascade fallback happened around the same turn.
</Step>
<Step title="Save the View">
If this is a recurring investigation, save your current column layout (Avg AI latency, Max latency, Latency (turns), LLM, LLM detail) as a named view for quick reuse next time.
</Step>
</Steps>
