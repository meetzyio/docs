# Call History

The Call History section provides a comprehensive view of all calls made by your AI agents. You can search, filter, and analyze call data to monitor performance and identify insights with powerful filtering capabilities, an audit/review workflow, and customizable views.

<Info>
A banner now sits at the very top of this page, letting you switch at any time between the **classic Call History table** and the **new, improved Calls view**. Both views are documented separately — this page covers the improved view; head over to [Call History (Classic)](/calls/call-history-classic) for a full walkthrough of the original table if you're using that view instead.
</Info>

<Info>
**New:** there's now an even more capable calls view available at **`/calls-v2`**, featuring fully configurable columns and additional filters beyond what's described below. If you've been living happily in the classic table, this is your reminder to come take a look — don't get stuck in the past like a photon trapped in a box. See the [Advanced Calls View](#configurable-columns) section on this page for the full breakdown of what's new.
</Info>

## Accessing Call History

Navigate to **Calls** in the main menu to access your complete call history. This now opens the improved calls view (**Calls v2**) by default.

<Info>
Calls v2 brings **fully configurable, drag-and-drop columns** (including dynamic input/output fields grouped by agent, with key columns pinned to the right edge), **saved views**, **real AI latency metrics with a per-turn detail chart**, an **expanded filter bar** (date presets, multi-agent selection, tag autocomplete, exact Call ID, latency range, and a one-click "suspicious calls" filter), a built-in **review/audit workflow** with per-call notes, and an **Excel export** that can target either all filtered calls or just your current selection.
</Info>

### Switching Between Views

A notice banner sits at the very top of the page reminding you that you're on the new Calls view.

<Steps>
<Step title="Notice the Banner">
At the top of the page, a highlighted banner reads "You're viewing the new Calls page."
</Step>
<Step title="Switch Back if Needed">
Click **Switch back to the classic view** in the banner to be taken to `/calls-old`, the original Call History table, if you run into something that doesn't yet behave as expected in the new view.
</Step>
<Step title="Return Anytime">
Both views read from the same underlying call data, so you can move back and forth between them without losing information — only view-specific preferences like column layout or saved views live separately per view.
</Step>
</Steps>

<Info>
This same toggle works in both directions: whether you land here from the main menu or arrive via a direct link, the banner at the top of the page always offers a one-click way back to the classic table, and the classic table offers an equivalent way forward into this improved view. See [Call History (Classic)](/calls/call-history-classic) for the documentation covering that table in detail.
</Info>

<Tip>
The banner is a safety net during the transition to the new view, not a permanent fixture — treat the classic view as a fallback rather than your primary workflow going forward.
</Tip>

## Configurable Columns

<Info>
The improved calls view lets you fully control which columns appear, in what order, and even add columns sourced directly from each agent's input parameters or structured output — no need to open a call individually to see a specific data point.
</Info>

Click the **⚙️ Columns** button above the table to open the column manager panel. It's organized into three areas:

| Section | Purpose |
|---------|---------|
| **Input columns** | Discover fields from each agent's input parameters (`call.data`) and add them as columns, grouped by agent |
| **Columns** | Manage visibility and order of all currently active columns — fixed and dynamic — via drag and drop |
| **Output columns** | Discover fields from each agent's structured output (`call.output`) and add them as columns, grouped by agent |

Saved column layouts live in the separate **👁️ Views** menu next to the Columns button — see [Saved Views](#saved-views) below.

<Steps>
<Step title="Open the Column Manager">
Click the **⚙️ Columns** button next to the Export to Excel button to open the column configuration drawer.
</Step>
<Step title="Reorder Columns">
In the **Columns** section, drag any row using the ⠿ handle to reorder it. The table updates its column order live as you drag.
</Step>
<Step title="Show or Hide Columns">
Use the checkbox next to each column name to toggle its visibility. Columns marked as non-toggleable (such as **Actions**) always remain visible.
</Step>
<Step title="Add a Dynamic Column from Input or Output">
Click **Input columns** or **Output columns**, find the field you need under the relevant agent group (grouped and collapsible per agent), and click **Add**. The field appears immediately as a new column, placed just before the pinned columns, and is tagged with an **input**/**output** badge in the Columns list.
</Step>
<Step title="Remove a Dynamic Column">
Dynamic columns display a small ✕ button next to their badge in the Columns list. Click ✕ to remove them from your view entirely.
</Step>
<Step title="Reset to Defaults">
Click **Reset to default columns** at the bottom of the panel to discard all customizations and restore the original column set.
</Step>
</Steps>

<Tip>
Your column configuration — order, visibility, and any dynamic columns you've added — is saved automatically per user and restored the next time you open the view. There's no manual save step.
</Tip>

<Warning>
Dynamic columns are tied to the agent and field path they were created from. If an agent stops sending a particular input or output field, that column will simply show empty values for calls where the data is missing, rather than being removed automatically.
</Warning>

### Pinned Columns

<Info>
A small number of columns are **pinned to the right edge** of the table so they stay visible regardless of how many columns you add or how far you scroll horizontally.
</Info>

By default, **Reviewed** and **Actions** are pinned. This keeps your audit status and row-level actions within reach even when you've added several dynamic input/output columns that push the table wide.

<Tip>
Pinned columns are visually grouped together at the right edge — if you rely heavily on the review workflow, keep the **Reviewed** column pinned rather than hiding it, so you always know which calls in view still need attention.
</Tip>

### Saved Views

<Info>
Beyond your single auto-saved layout, the **👁️ Views** menu (next to the Columns button in the header) lets you keep multiple **named views** — for example, one focused on latency troubleshooting and another focused on audit review — and switch between them instantly.
</Info>

<Steps>
<Step title="Configure a Layout">
Show, hide, reorder, and add dynamic columns until the table matches the view you want to save.
</Step>
<Step title="Open the Views Menu">
Click **👁️ Views** in the header to open the saved views panel.
</Step>
<Step title="Name and Save">
Type a name into the **New view name…** field and click **Save current**. The current column configuration is stored as a new saved view.
</Step>
<Step title="Apply a Saved View">
Click on any saved view's name in the list to instantly replace your current column configuration with that view's layout.
</Step>
<Step title="Delete a Saved View">
Click the ✕ next to a saved view to remove it. This only deletes the saved view itself — it doesn't change your currently active columns.
</Step>
</Steps>

<Tip>
Saved views only capture the **column configuration** (which columns, their order, and visibility) — they don't store filters, sorting, or page size. Combine a saved view with a filter preset for a fully repeatable workflow.
</Tip>

### Legacy Column Configuration Migration

<Info>
If you previously customized columns in the classic Call History table, that layout isn't lost — the improved view automatically imports it the first time you open it.
</Info>

The first time a user opens the improved calls view without any existing saved preferences, the system performs a **one-time, automatic migration**:

| Step | What happens |
|------|--------------|
| 1 | The improved view checks your browser's local storage for a legacy column configuration saved from the classic Call History table |
| 2 | Fixed columns that exist in both the old and new default sets carry over their visibility setting |
| 3 | Any dynamic input or output columns you had added in the classic table are reconstructed as-is, keeping their label, path, and source |
| 4 | Your previous sort column, sort direction, and page size are applied if present |
| 5 | The migrated configuration is saved to your account immediately, so it's available even if you switch devices or browsers afterward |

<Warning>
This migration is read-only and runs only once. It reads from the browser's local storage, so it only applies on the same browser/device where you originally customized the classic table. If you've already opened the improved view before, or already have saved preferences for it, the migration is skipped and your existing improved-view configuration is used instead.
</Warning>

## Review & Audit Workflow

<Info>
Every call can now be marked as reviewed and annotated with a free-text note directly from the table — no need to leave Call History to track your QA process.
</Info>

The **Reviewed** column (pinned to the right by default) is the entry point for the audit workflow:

| Element | Description |
|---------|-------------|
| **Reviewed toggle** | Marks the call as reviewed or not yet reviewed, visually distinguished in the column |
| **Note popover** | An inline editor attached to the Reviewed column where you can write a free-text audit note for that specific call |
| **Auto-save** | Notes are saved automatically shortly after you stop typing, without a separate save button |

<Steps>
<Step title="Open the Review Popover">
Click the **Reviewed** cell for any call to open its inline note editor.
</Step>
<Step title="Mark as Reviewed">
Toggle the call's reviewed status to indicate it has been audited.
</Step>
<Step title="Write an Audit Note">
Type your observations, findings, or QA comments directly into the note field. Your input is debounced and saved automatically a moment after you stop typing.
</Step>
<Step title="Close the Popover">
Click anywhere outside the popover to close it. Only one review popover can be open at a time, so opening a new one automatically closes any other that was active.
</Step>
<Step title="Revisit Later">
Reopen the Reviewed cell for any call at any time to read or edit the existing note — your review history for that call is preserved.
</Step>
</Steps>

<Tip>
Combine the Reviewed column with a saved filter preset (for example "Failed + Last 7 Days") and a saved column view that keeps **Reviewed** and **Tags** visible, to build a repeatable QA sweep: filter down to the calls you need to audit, review each one, leave a note, and move to the next.
</Tip>

<Warning>
Review status and notes are stored per call and are visible to anyone with access to Call History — treat audit notes as shared team documentation rather than private scratch notes.
</Warning>

## AI Latency Metrics

<Info>
Every call now tracks how quickly your AI agent responded throughout the conversation, giving you a direct signal of conversational responsiveness independent of call outcome or duration.
</Info>

The improved view surfaces AI latency at three levels of detail:

| Metric | Column | Description |
|--------|--------|-------------|
| **Average latency** | Avg AI latency | The mean AI response latency (in milliseconds) across all turns in the call |
| **Maximum latency** | Max latency | The single highest response latency recorded during the call — useful for spotting worst-case delays |
| **Per-turn sparkline** | Latency (turns) | A compact inline chart showing how latency evolved turn by turn, without leaving the table |

<Steps>
<Step title="Scan Averages at a Glance">
Sort the table by **Avg AI latency** to quickly identify calls or agents with consistently slow responses.
</Step>
<Step title="Spot Outliers with Max Latency">
Enable the **Max latency** column (hidden by default) to catch calls with an isolated but severe delay that the average might hide.
</Step>
<Step title="Read the Sparkline">
The **Latency (turns)** column renders a lightweight line for each call, plotting latency per turn. A rising line toward the end of a call can indicate the agent slowing down as the conversation got more complex.
</Step>
<Step title="Open the Full Latency Detail Modal">
Click into a call's details to open the dedicated AI latency modal: a full, interactive chart plotting latency per turn, with exact millisecond values on hover and the timestamp of each turn along the X axis.
</Step>
</Steps>

### Latency Detail Modal

<Info>
The latency detail modal turns the compact table sparkline into a full-size, turn-by-turn chart so you can pinpoint exactly where a call slowed down.
</Info>

| Feature | Description |
|---------|-------------|
| **Per-turn chart** | Every AI turn in the call is plotted as a point, connected in chronological order |
| **Exact values on hover** | Hovering a point shows the precise latency in milliseconds for that specific turn |
| **Timestamp axis** | The X axis reflects when each turn occurred during the call, making it easy to correlate spikes with a stage of the conversation |
| **Visual outlier detection** | Sudden jumps in the line stand out immediately compared to scanning raw numbers in a table |

<Tip>
Combine latency metrics with the LLM and LLM detail columns to check whether latency spikes correlate with a model cascade fallback — a secondary model taking over mid-call can sometimes explain a sudden increase in response time. Open the latency detail modal and the LLM detail breakdown side by side for the same call to confirm.
</Tip>

<Warning>
Latency data depends on the underlying voice provider reporting response timing for each turn. Calls made before latency tracking was enabled, or through integrations that don't report this data, will show empty values for these columns and an empty chart in the detail modal.
</Warning>

## Recording Player with Waveform

<Info>
The recording player has been upgraded from a simple audio control to a full waveform-based player, built from the actual decoded audio of the call — not a generic placeholder animation. It also includes a rich, per-turn conversational view when detailed provider data is available.
</Info>

Click the **Recording** column on any call to open the player modal, which includes:

| Feature | Description |
|---------|-------------|
| **Real waveform** | Rendered directly from the decoded audio, showing actual amplitude across the call |
| **Click-to-seek** | Click anywhere on the waveform to jump to that point in the recording |
| **Playback progress** | The waveform visually fills in as the recording plays, distinguishing played from unplayed audio |
| **Skip controls** | Jump backward or forward 10 seconds with dedicated buttons |
| **Playback speed** | Choose from 0.5x, 0.75x, 1x, 1.25x, 1.5x, or 2x speed |
| **Rich synced transcript** | Per-turn transcript with latency badges (ASR, TTS, LLM), the LLM model used, and expandable tool call/result details, when available |
| **Fallback transcript** | Falls back to a plain text transcript automatically if detailed per-turn provider data isn't available for that call |
| **Download** | Download the recording file directly from the modal |

<Steps>
<Step title="Open the Player">
Click the Recording column for any call with an available recording.
</Step>
<Step title="Review the Waveform">
Wait for the audio to load and decode — the waveform renders automatically once ready, reflecting the real amplitude of the call.
</Step>
<Step title="Seek and Adjust Speed">
Click on any part of the waveform to jump there instantly, or use the speed buttons to review a section more quickly or more carefully.
</Step>
<Step title="Cross-Reference with the Transcript">
Use the transcript panel next to the player to follow along with what's being said as you scrub through the recording. Expand latency or tool badges on any turn for a deeper technical breakdown of that moment in the call.
</Step>
</Steps>

<Tip>
Because the waveform is built from decoded audio rather than a static image, longer recordings may take a moment to render on first open. Once decoded, seeking and speed changes are instant.
</Tip>

## Excel Export

<Info>
Exporting to Excel respects exactly what you see: only the columns currently visible in your table — in the order you've arranged them — are included in the exported file, including any dynamic input/output columns you've added and the current review status/notes.
</Info>

Two export options are available side by side in the header:

| Button | Scope |
|--------|-------|
| **Export to Excel** | Exports every call matching your current filters, across all pages |
| **Export selection (N)** | Appears only once you've checked one or more rows; exports only those selected calls |

<Steps>
<Step title="Configure Your View">
Use the column manager to show, hide, and reorder columns until the table reflects exactly the data you want to export. Apply a saved view first if you have one ready for this purpose.
</Step>
<Step title="Apply Your Filters">
Narrow down the calls you want using the filter bar, since the full export follows the currently filtered result set.
</Step>
<Step title="Choose Full or Selective Export">
Click **Export to Excel** to export every filtered call, or select specific rows with the checkboxes and click **Export selection (N)** to export only those calls — useful when you've hand-picked a set of calls during a review session.
</Step>
<Step title="Watch the Export State">
The button shows an "Exporting…" state while the file is being generated.
</Step>
<Step title="Open the File">
The downloaded spreadsheet mirrors your visible columns and their order, including any dynamic agent input/output fields you've added and the Reviewed status/notes, making it easy to share exactly the view you were working with.
</Step>
</Steps>

<Tip>
"Export selection" is a natural companion to the review workflow: mark and annotate the calls you've audited, select them, and export just that batch as a record of your QA pass — without pulling in every other call matching your filters.

## Advanced Filter System

### Filter Visibility Configuration

<Info>
Customize which filters are visible in your interface to streamline your workflow and focus on the most relevant filtering options.
</Info>

A dedicated **⚙️ settings button** is located at the end of the Filter Bar, next to the filter controls. It opens a configuration panel that lets you show or hide individual filters without affecting your applied filter values.

<Steps>
<Step title="Open Filter Settings">
Click the ⚙️ settings icon at the right end of the Filter Bar to open the filter visibility panel.
</Step>
<Step title="Toggle Individual Filters">
Use the checkboxes to show or hide each of the following filters independently:

- **Goal** — filter calls by the agent's configured goal or objective
- **Tags** — filter by dynamic or custom tags
- **Evaluations** — filter by evaluation completion or outcome
- **Call ID** — the direct database lookup search field, matched on the exact ID

Core filters such as Date Range, Agents, Status, Direction, Success, Latency range, and Suspicious calls are always visible and cannot be hidden, since they are considered essential for everyday use.
</Step>
<Step title="Apply and Close">
Close the panel by clicking outside of it or pressing the settings icon again. Hidden filters are immediately removed from the Filter Bar, freeing up space for the ones you actually use.
</Step>
<Step title="Automatic Persistence">
Your filter visibility preferences are saved automatically per user and restored the next time you open Call History — no need to reconfigure them on every visit.
</Step>
</Steps>

<Info>
By default, the **Tags** filter is visible in the Filter Bar out of the box, so you don't need to open the settings panel to start filtering calls by tags. Goal, Evaluations, and Call ID remain part of the same visibility configuration and follow their own default state, which you can adjust at any time.
</Info>

<Tip>
If a filter is hidden but has an active value from a previous session, it will remain applied to your results even though it's not visible. Re-enable the filter from the settings panel to review or clear it. Look for the 👁️ **Hidden Filter** indicator near the settings icon — it appears whenever a hidden filter still holds an active value, so you always know your results are being narrowed by something you can't currently see.
</Tip>

### Suspicious Calls Filter

<Info>
The "Suspicious calls" filter is a one-click way to surface calls that are more likely to need a closer look, without manually combining several filters yourself.
</Info>

Enabling this filter highlights calls that match **any** of the following conditions:

| Condition | Why it's flagged |
|-----------|-------------------|
| High average latency | The call's average AI response latency exceeds a built-in threshold (3000 ms) |
| Problematic status | The call ended as **no-answer**, **failed**, or **blocked** |
| Goal not met | The call's evaluations indicate its configured goal wasn't achieved |
| Missing transcript | No transcript was captured for the call at all |

<Steps>
<Step title="Enable the Filter">
Toggle **Suspicious calls** on in the Filter Bar.
</Step>
<Step title="Review the Narrowed Results">
The table updates to show only calls matching at least one of the suspicious conditions above.
</Step>
<Step title="Investigate Each Call">
Open each flagged call's details, recording, or latency chart to determine whether it needs a review note, a tag, or escalation.
</Step>
<Step title="Mark as Reviewed">
Use the **Reviewed** column to mark calls you've checked and leave an audit note, so the next pass through your suspicious calls doesn't re-cover the same ground.
</Step>
</Steps>

<Info>
Unlike Min/Max latency or Status, which apply a strict AND to your other filters, "Suspicious calls" applies an **OR** across its own internal conditions — a call needs to match only one of them to show up, since each condition on its own is a reasonable independent signal of a problematic call.
</Info>

<Tip>
Combine "Suspicious calls" with a date range like **Today** or **Last 24 hours** to build a quick daily triage habit: check what's suspicious since yesterday, review it, and clear the queue.
</Tip>

### Exact Call ID Search

<Warning>
When using Call ID search, all other filters are temporarily disabled to ensure precise lookups.
</Warning>

The Call ID filter performs a **direct, exact-match** database lookup and has **exclusive priority over every other filter** in the Filter Bar. As soon as you start typing a value into the Call ID field, all remaining filters (Date Range, Agents, Status, Direction, Success, Goal, Tags, Evaluations, Latency range, and Suspicious calls) become visually disabled and are excluded from the query — the interface greys them out and blocks interaction with them to make it clear that only the Call ID lookup is active.

<Info>
Think of it as a small measurement problem: the moment you observe the system through a Call ID, every other possible filter state "collapses" — much like a quantum measurement collapsing a wave function into a single outcome. Before you type an ID, the Filter Bar exists in a superposition of Date Range, Agents, Status, Direction, Success, Goal, Tags, Evaluations, Latency range, and Suspicious calls, all potentially active at once. The instant a Call ID value is present, that superposition resolves into a single, deterministic state: exactly one call, found by its exact ID, with no other filter contributing to the result.
</Info>

Enhanced Call ID functionality with database search:

<Steps>
<Step title="Enter Call ID">
Type the specific call ID in the dedicated search field. You can also copy an ID directly from the **Call ID** column's compact badge (or the row's Copy ID quick action) and paste it here. As soon as a value is present, the rest of the filters switch to a disabled visual state.
</Step>
<Step title="Database Query">
The system performs a direct database lookup for the exact call ID, ignoring any values currently set in other filters. Partial or fuzzy matches are not returned — the ID must match exactly.
</Step>
<Step title="Instant Results">
The matching call is displayed immediately, bypassing all other filters.
</Step>
<Step title="Clear Search">
Remove the call ID to restore normal filtering functionality. All previously configured filters are automatically re-enabled and reapplied — the "superposition" is restored exactly as you left it.
</Step>
</Steps>

<Tip>
Like the Goal and Evaluations filters, the Call ID field is hidden from the Filter Bar by default and can be enabled from the filter visibility settings (⚙️) whenever your workflow requires manual, exact ID lookups.
</Tip>

<Warning>
This priority behavior is exclusive and non-negotiable: while a Call ID value is present, there is no way to combine it with Date Range, Agents, Status, Direction, Success, Goal, Tags, Evaluations, Latency range, or Suspicious calls. If you need a combined search, clear the Call ID field first and use the other filters instead.
</Warning>

<Info>
Filter calls by dynamic tags that are automatically generated based on call content, outcomes, and agent behaviors, using a chip-based multi-select field with live autocomplete.
</Info>

<Steps>

</Step>
<Step title="Select a Suggested Tag">

The tags filter provides:

- **Autocomplete Suggestions** - Existing tags are suggested as you type, so you don't need to remember exact spelling
- **Multi-Select Capability** - Select multiple tags to find calls matching any or all criteria
- **Real-time Updates** - Tag list updates as new calls are processed
- **Custom Tag Support** - Manual tags can be added to calls for additional categorization

<Info>
The Tags filter is **visible by default** in the Filter Bar, so it's ready to use as soon as you open Call History. You can still hide it from the ⚙️ filter settings panel if you prefer a more minimal filter set. Like all other filters, it is temporarily disabled while a Call ID search is active.
</Info>

### LLM and LLM Detail Columns

<Info>
These two columns surface the underlying language model activity for every call, which is especially useful for agents built on ElevenLabs' conversational stack, where a **model cascade** can automatically fall back to a secondary model mid-call if the primary one becomes unavailable or degrades.
</Info>

| Column | What it shows |
|--------|---------------|
| **LLM** | The distinct model(s) used during the call, listed in the order they were engaged (e.g. a single model like `gpt-4o`, or multiple models such as `gpt-4o + gpt-4o-mini` if a fallback occurred). |
| **LLM detail** | An expandable, turn-by-turn breakdown showing exactly which model handled each conversational turn and at what point in the call the switch happened. |

<Steps>
<Step title="Enable the Columns">
Open the column manager above the Call Table and toggle on **LLM** and/or **LLM detail** to add them to your view.
</Step>
<Step title="Read the LLM Column">
Each row shows the model(s) used for that call. A single model name means the call ran entirely on the primary model with no fallback.
</Step>
<Step title="Spot Degradations">
When a call shows **more than one model** in the LLM column, it means the ElevenLabs cascade degraded at least once during the call — falling back from the primary model to a secondary one. This is the same detection logic used in the call details modal.
</Step>
<Step title="Drill Into LLM Detail">
Expand the LLM detail column (or open the call in the Details Modal) to see the exact timestamp of each turn and which model produced it, helping you pinpoint when and why a degradation happened.
</Step>
</Steps>

<Tip>
Use the LLM column together with the Status and Success filters to quickly check whether cascade degradations correlate with lower success rates or specific agents, then dig deeper with LLM detail on the affected calls.
</Tip>

<Warning>
For calls made before model cascade tracking was introduced, the LLM column falls back to the legacy single `model_used` value when no multi-model data is available. In that case, no degradation can be detected for those older calls.
</Warning>
